**Feature Branch**: `002-v2-major-update`  
**Created**: 2026-02-10

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 社團升級系統 (Priority: P1)

作為同人社團經營者，我希望能在每輪場次結束後升級社團的各種能力，讓我能夠制定長期經營策略，提升社團的整體營運能力。

**Why this priority**: 社團升級系統是v2的核心機制，提供玩家長期成長目標和策略深度，直接影響遊戲的可玩性和重玩價值。

**Independent Test**: 可以透過完成一個場次後進入社團管理介面，購買任意升級項目，然後在下一個場次中觀察升級效果是否正確套用。

**Acceptance Scenarios**:

1. **Given** 場次結束後，**When** 玩家進入社團管理介面，**Then** 看到所有可升級項目、當前等級、升級費用和效果說明
2. **Given** 玩家有足夠資金，**When** 點擊升級按鈕，**Then** 扣除對應費用並提升等級
3. **Given** 玩家資金不足，**When** 嘗試升級，**Then** 顯示資金不足提示，無法升級
4. **Given** 升級項目已達最高等級，**When** 查看該項目，**Then** 顯示「已達最高等級」狀態

---

### User Story 2 - 場次隨機事件系統 (Priority: P1)

作為玩家，我希望在場次進行中遇到各種隨機事件，讓每次場次體驗都有不同的驚喜或挑戰，增加遊戲的不確定性和趣味性。

**Why this priority**: 隨機事件系統大幅提升遊戲的重玩價值和沉浸感，模擬真實同人場次的各種突發狀況。

**Independent Test**: 進行一場販售場次，觀察是否觸發隨機事件，事件效果是否正確套用於銷售結果。

**Acceptance Scenarios**:

1. **Given** 場次進行中，**When** 系統觸發隨機事件，**Then** 顯示事件通知，包含事件名稱、描述和影響效果
2. **Given** 觸發負面事件（如大雨），**When** 計算銷售結果，**Then** 對應參數（如來客數）正確減少
3. **Given** 觸發正面事件（如網紅推薦），**When** 計算銷售結果，**Then** 對應參數（如銷量）正確增加
4. **Given** 事件涉及特定作品，**When** 顯示事件通知，**Then** 顯示該作品的完整名稱而非「某作品」

---

### User Story 3 - 最大銷售量機制與小幫手系統 (Priority: P1)

作為玩家，我希望遊戲能模擬真實攤位的人力限制，讓我理解僱用小幫手的重要性，並在銷量超出能力時收到明確提示。

**Why this priority**: 增加遊戲的策略深度，讓玩家需要平衡印量與人力配置，避免高人氣作品銷量不合理地高（如2000本）。

**Independent Test**: 創建一個高人氣作品，不升級小幫手，觀察銷量是否被限制在最大值，並收到「分身乏術」提示。

**Acceptance Scenarios**:

1. **Given** 玩家未升級小幫手，**When** 潛在銷量超過基礎上限，**Then** 實際銷量被限制在上限值
2. **Given** 銷量達到上限，**When** 場次結算顯示，**Then** 提示「因為太忙導致分身乏術，部分顧客無法完成購買」
3. **Given** 玩家升級小幫手等級，**When** 下一場次開始，**Then** 銷售上限對應提升

---

### User Story 4 - 庫存管理與倉儲成本 (Priority: P2)

作為玩家，我希望能管理我的庫存，決定是否銷毀滯銷作品，同時承擔倉儲成本的壓力，模擬真實同人社團的經營挑戰。

**Why this priority**: 增加經營的現實感和策略深度，讓玩家需要考慮長期庫存管理。

**Independent Test**: 場次結束後進入庫存管理介面，銷毀一個作品的庫存，觀察該作品在下一次場次中是否以固定低人氣繼續銷售。

**Acceptance Scenarios**:

1. **Given** 場次結束後，**When** 進入社團管理介面，**Then** 看到所有作品的庫存量和每單位倉儲成本
2. **Given** 選擇銷毀某作品庫存，**When** 確認銷毀，**Then** 庫存清零，該作品人氣固定為當前值且無法再繪製新作
3. **Given** 場次結算時，**When** 計算倉儲成本，**Then** 根據總庫存量和升級等級扣除正確費用
4. **Given** 倉儲成本使資金變成負數，**When** 結算完成，**Then** 觸發負債遊戲結束流程

---

### User Story 5 - 遊戲結束與負債系統 (Priority: P2)

作為玩家，我希望在資金變成負數時收到清晰的遊戲結束提示，了解失敗原因並有機會重新開始。

**Why this priority**: 提供明確的失敗條件和遊戲結束體驗，增加遊戲的緊張感。

**Independent Test**: 故意讓資金因倉儲成本或其他費用變成負數，觀察遊戲是否正確顯示結束畫面。

**Acceptance Scenarios**:

1. **Given** 場次結算後資金為負，**When** 結算完成，**Then** 顯示遊戲結束畫面
2. **Given** 遊戲結束畫面，**When** 顯示內容，**Then** 包含失敗原因說明、最終數據統計、重新開始按鈕
3. **Given** 使用天使投資人舉債，**When** 場次結算時仍有負債，**Then** 同樣觸發負債遊戲結束

---

### User Story 6 - 開發者除錯日誌 (Priority: P2)

作為開發者，我希望能在後台看到各作品的詳細參數和計算過程，方便驗證人氣計算和銷量計算是否正確。

**Why this priority**: 解決當前反饋的銷量異常問題（如單回合高人氣作品賣2000本），提供除錯工具加速問題定位。

**Independent Test**: 開啟開發者模式，進行一場販售，在日誌中查看每個作品的人氣、密度、購買力、銷量計算過程。

**Acceptance Scenarios**:

1. **Given** 開發者模式啟用，**When** 場次進行中，**Then** 後台顯示即時參數日誌
2. **Given** 查看日誌，**When** 檢視作品資訊，**Then** 顯示人氣值、市場密度、顧客購買力、預估銷量、實際銷量
3. **Given** 銷量計算完成，**When** 查看計算過程，**Then** 顯示各個乘數和加成的詳細分解

---

### User Story 7 - 詳細場次結算報告 (Priority: P2)

作為玩家，我希望在場次結束時看到每種刊物的詳細銷售狀況，而不只是總結果，讓我能分析哪些作品表現好、哪些需要調整策略。

**Why this priority**: 提升玩家的決策資訊，幫助玩家了解市場反應並制定更好的策略。

**Independent Test**: 完成一個場次，在結算畫面查看是否顯示每種刊物的獨立銷售數據和收益。

**Acceptance Scenarios**:

1. **Given** 場次結束，**When** 顯示結算報告，**Then** 列出每種刊物的銷售數量、單價、收益
2. **Given** 結算報告顯示，**When** 有多種刊物，**Then** 按銷量或收益排序顯示，並顯示總計
3. **Given** 發生隨機事件，**When** 顯示結算報告，**Then** 標註受事件影響的作品及影響程度

---

### User Story 8 - 銷量預估準確度調整 (Priority: P3)

作為玩家，我希望銷量預估不再過於準確，特別是在市場了解度低的時候，讓我需要花時間研究市場才能做出更好的決策。

**Why this priority**: 增加遊戲的不確定性和市場研究的重要性，提升策略深度。

**Independent Test**: 在市場了解度低的狀態下查看銷量預估，觀察預估值與實際銷量的差異是否較大。

**Acceptance Scenarios**:

1. **Given** 市場了解度低，**When** 查看銷量預估，**Then** 預估值基於人氣而非密度和購買力計算，可能有較大誤差
2. **Given** 市場了解度高，**When** 查看銷量預估，**Then** 預估值更接近實際銷量
3. **Given** 預估與實際有差異，**When** 差異過大，**Then** 結算時顯示「市場反應超出預期」或「銷量不如預期」提示

---

### User Story 9 - 作品衰退度機制 (Priority: P3)

作為玩家，我希望作品有衰退度屬性，讓我能區分「蹭熱度的時事作品」和「長青經典作品」，制定不同的經營策略。

**Why this priority**: 增加作品屬性的多樣性，讓玩家需要考慮作品的長期價值。

**Independent Test**: 創建高衰退度和低衰退度的作品，經過數輪場次後比較人氣下降的速度。

**Acceptance Scenarios**:

1. **Given** 創建作品時，**When** 選擇題材，**Then** 根據題材自動設定衰退度（時事題材高衰退，經典題材低衰退）
2. **Given** 高衰退度作品，**When** 每輪結束時，**Then** 人氣大幅下降（如50點/輪）
3. **Given** 低衰退度作品，**When** 每輪結束時，**Then** 人氣緩慢下降
4. **Given** 查看作品資訊，**When** 顯示詳情，**Then** 包含衰退度指標和預估人氣走勢

---

### User Story 10 - 顧客類型差異化吸引力 (Priority: P3)

作為玩家，我希望封面和紙質對不同類型顧客有不同的吸引效果，讓我能針對目標客群選擇最適合的印刷品質。

**Why this priority**: 增加遊戲的策略深度，讓封面和紙質的選擇更有意義。

**Independent Test**: 使用不同封面等級的作品，觀察對一般顧客和狂熱粉絲的停留機率影響差異。

**Acceptance Scenarios**:

1. **Given** 一般路人顧客，**When** 遇到精美封面作品，**Then** 停留機率大幅提升
2. **Given** 狂熱粉絲顧客，**When** 遇到喜愛題材的作品，**Then** 無論封面品質都有高停留機率
3. **Given** 精打細算型顧客，**When** 評估作品，**Then** 更重視紙質的性價比
4. **Given** 開發者日誌啟用，**When** 計算停留機率，**Then** 顯示各顧客類型的係數和計算過程

---

### User Story 11 - 擴充封面與紙質選項 (Priority: P3)

作為玩家，我希望有更多封面和紙質選項，讓我能根據預算和目標客群做出更細緻的選擇。

**Why this priority**: 豐富遊戲的選擇空間，提供更多經營策略可能性。

**Independent Test**: 創建新作品時查看封面和紙質選項，確認新的級距和定價都正確顯示。

**Acceptance Scenarios**:

1. **Given** 創建作品時選擇紙質，**When** 顯示選項，**Then** 提供四個等級：經濟（-20%吸引力）、標準（0%）、優質（+20%）、豪華（+50%）
2. **Given** 創建作品時選擇封面，**When** 顯示選項，**Then** 提供四個等級：免費（自製）、基礎（$500）、精緻（$2000）、頂級（$10000）
3. **Given** 選擇封面等級，**When** 確認選擇，**Then** 正確扣除對應費用並套用吸引力加成

---

### User Story 12 - 程式碼模組化重構 (Priority: P4)

作為開發者，我希望將過長的單一HTML檔案拆分成多個模組，方便維護和未來功能擴展。

**Why this priority**: 技術債務清理，雖不直接影響玩家體驗，但對長期維護至關重要。

**Independent Test**: 重構後執行所有現有功能，確認遊戲行為與重構前完全一致。

**Acceptance Scenarios**:

1. **Given** 重構完成，**When** 執行遊戲，**Then** 所有現有功能正常運作
2. **Given** 查看程式碼結構，**When** 檢視檔案組織，**Then** 根據功能階段（創作、印刷、場次、結算等）合理分割
3. **Given** 需要修改特定功能，**When** 定位相關程式碼，**Then** 能快速找到對應的模組檔案

---

### Edge Cases

- 當玩家同時觸發多個隨機事件時，效果如何疊加？ -> 重複疊加(因此效果限定在對參數的加減)
- 當升級「天使投資人」後舉債印刷，但場次銷量不足以還債時如何處理？->場次結束結算負債時觸發遊戲結束
- 當所有作品都被銷毀庫存時，玩家是否還能繼續遊戲？ -> 視為沒有庫存，可以選擇跳過場次
- 當「最大銷售量」在事件加成後仍然觸發上限時，損失如何計算？ -> 不要設計會影響最大銷售量的事件
- 當股市投資遇到「台股大跌」事件時，是否會損失本金？ -> 不會，投資技術高超因此能避開損失
- 當封面成本超過玩家資金時，是否允許舉債？ -> 除非有天使投資人，否則不能舉債

## Requirements *(mandatory)*

### Functional Requirements

#### 社團升級系統

- **FR-001**: 系統 MUST 在每輪場次結束後提供社團管理介面
- **FR-002**: 系統 MUST 支援以下升級項目，每項有多個等級：
  - 培訓小幫手：提升單場最大銷售量上限
  - 僱傭Coser小幫手：提升顧客停留機率
  - Adobe排版課程：提升刊物吸引力
  - 老家倉儲：降低倉儲成本
  - 親友團：提供每種刊物最小銷量保證
  - 社群經營：根據原本銷量提升總體銷量（乘數效果）
  - 天使投資人：提供舉債額度
  - 股市投資：根據持有資金獲得利息
  - 提升文筆：無實質效益的趣味升級
- **FR-003**: 系統 MUST 顯示每個升級項目的當前等級、升級費用、效果說明

#### 隨機事件系統

- **FR-004**: 系統 MUST 在場次進行中隨機觸發事件
- **FR-005**: 系統 MUST 支援至少20種不同事件，正面負面各半
- **FR-006**: 系統 MUST 提供可擴展的事件模板格式，方便後續添加新事件
- **FR-007**: 事件通知 MUST 顯示具體作品名稱而非「某作品」

#### 開發者工具

- **FR-008**: 系統 MUST 提供開發者日誌功能，顯示各作品的詳細參數
- **FR-009**: 開發者日誌 MUST 包含人氣值、市場密度、購買力、銷量計算過程

#### 庫存與倉儲

- **FR-010**: 系統 MUST 允許玩家在場次結束後銷毀任意作品的庫存
- **FR-011**: 被銷毀庫存的作品 MUST 以固定人氣繼續銷售，不能再創作新作
- **FR-012**: 系統 MUST 在場次結算時扣除倉儲成本

#### 遊戲結束機制

- **FR-013**: 系統 MUST 在資金變成負數時觸發遊戲結束
- **FR-014**: 遊戲結束畫面 MUST 顯示失敗原因、最終數據、重新開始選項

#### UI改進

- **FR-015**: 場次結算 MUST 顯示每種刊物的個別銷售數量和收益
- **FR-016**: 隨機事件通知 MUST 顯示完整作品名稱

#### 遊戲機制

- **FR-017**: 系統 MUST 實施最大銷售量限制，受小幫手等級影響
- **FR-018**: 達到銷售上限時 MUST 顯示「分身乏術」提示
- **FR-019**: 系統 MUST 根據市場了解度調整銷量預估準確度
- **FR-020**: 系統 MUST 為每個作品設定衰退度屬性
- **FR-021**: 高衰退度作品 MUST 以更快速度失去人氣

#### 封面與紙質系統

- **FR-022**: 系統 MUST 根據顧客類型調整封面和紙質的吸引力效果
- **FR-023**: 紙質 MUST 提供四個等級：-20%、0%、+20%、+50% 吸引力效果
- **FR-024**: 封面 MUST 提供四個等級：免費、$500、$2000、$10000

#### 程式碼架構

- **FR-025**: 程式碼 MUST 按功能階段拆分成多個檔案
- **FR-026**: 重構後 MUST 保持所有現有功能正常運作

### Key Entities

- **社團 (Circle)**: 玩家經營的同人社團，包含資金、升級等級、作品列表
- **升級項目 (Upgrade)**: 可購買的社團能力提升，包含名稱、等級上限、費用曲線、效果描述
- **隨機事件 (Event)**: 場次中發生的事件，包含名稱、描述、觸發條件、效果類型、影響參數
- **作品 (Work)**: 玩家創作的刊物，新增衰退度、封面等級、紙質等級屬性
- **顧客類型 (CustomerType)**: 不同消費者類型，各有不同的封面/紙質敏感度係數

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 玩家可在場次結束後 3 次點擊內進入社團管理介面並完成任意升級
- **SC-002**: 每場場次有 30%-50% 機率觸發至少一個隨機事件
- **SC-003**: 開發者日誌能顯示足夠資訊，使開發者在 5 分鐘內定位銷量計算異常
- **SC-004**: 單場最高銷量在合理範圍內（未升級小幫手時不超過 200 本/輪）
- **SC-005**: 低市場了解度時，銷量預估誤差至少 30%；高了解度時誤差低於 10%
- **SC-006**: 高衰退度作品在 3-5 輪內人氣下降至少 50%
- **SC-007**: 重構後所有原有測試案例通過率維持 100%
- **SC-008**: 程式碼檔案數量從 1 個增加到至少 5 個模組
- **SC-009**: 場次結算報告載入時間不超過 2 秒

## Assumptions

1. **升級費用曲線**: 假設採用指數成長曲線，各升級項目的詳細數值將在設計階段確定
2. **隨機事件觸發率**: 假設基礎觸發率為 20%/場次，可透過遊戲設定調整

4. **股市投資收益**: 假設為固定利率，不實作股市波動機制
5. **程式碼重構**: 假設重構僅涉及檔案拆分，不改變現有功能邏輯
6. **最大銷售量上限**: 假設基礎值為 100 本/輪，每級小幫手增加 50 本
7. **顧客類型係數**: 假設現有顧客類型系統已定義，新機制只是調整係數

const eventTemplate = {

  type: "negative",          // positive/negative
  category: "weather",       // weather/neighbor/accident/celebrity/social/market/controversy
  effects: [
    { 
      target: "visitor_count",    // 影響的參數
      modifier: "multiply",       // add/multiply/set
      value: 0.6,                 // 影響值
      scope: "all"                // all/specific_work/random_work
    }
  ],
  triggerConditions: {
    minRound: 1,              // 最早觸發輪數
    maxRound: null,           // 最晚觸發輪數（null=無限）
    probability: 0.05,        // 觸發機率
    exclusive: ["event_002"]  // 互斥事件
  },
  notification: {
    title: "☔ 傾盆大雨",

  }
};
